# 実機確認 (spikes)

マイルストーン 1〜3 で実機の振る舞いを確かめるためのスケッチと、その結果。
コードは参考として残す。**本体ファームの設計に効く事実はここに書き、`docs/設計.md` と `CLAUDE.md` にも反映する。**

## M1 ブリングアップ (`m1_bringup/`) — 2026-09-12

### 実機の素性

- esptool 5.3.1 `flash-id`: **ESP32-P4 revision v1.3** / Dual Core + LP Core / 水晶 40MHz / USB-Serial/JTAG / フラッシュ 16MB / MAC `e8:f6:0a:e2:f7:0e`
  → **`ChipVariant=prev3` で正しい**
- esptool は **5.3.1 を版指定で使う。** 同じフォルダに 4.5.1 もあり、glob で先に拾われるが ESP32-P4 を知らない
- 工場ファームは退避済み: `tools/out/factory_backup_e8f60ae2f70e.bin` (16MB, SHA256 `A260EDA93E4E5DDC1D3ABDDD361B1EB326C07D4248B67D1B493FEBA057FDE231`, git 管理外)。
  書き戻すときは `esptool --port COM3 write-flash 0 <bin>`
- 工場ファームは USB シリアルに何も出さない (6 秒読んで 0 行)

### スケッチを焼いて分かったこと

- ビルド: 2,116,706 バイト (APP 6.4MB の 32%)。書き込み 15 秒
- `M5.getBoard()` = 22 / `ESP.getChipRevision()` = 103 / CPU 360MHz / PSRAM 33,554,432 (空き 29.8MB) / SDK v5.5.5 / RTC・スピーカー有効
- **画面は `rotation=0` で縦 720×1280。** 左上 (赤) / 右下 (青) の目印がそのとおりの位置に出る
- `lgfxJapanGothicP_40` で `ABCDEFGHIJKLMNO` (15 文字) が約 490px、`1234567 23時間前` が約 460px。720px 幅の 1 行に収まる
- **`tools/serial.ps1` (DTR/RTS を落として開く) で読み書きしてもチップは落ちなかった**。スクリーンショット (PNG 17,840 バイト) も取れた
- Port A の I2C スキャン: **0x21 (QR) あり / 0x29 (ToF) なし** (ToF は未着なので想定どおり)

### 踏んだこと: M5Unified の外付けディスプレイ検出が Port A を奪う

- 症状: 起動直後のスキャンは通るのに、QR の `getDecodeReadyStatus()` が毎回 `0xFF` (I2C 失敗)。`setTriggerMode` の読み戻しも失敗。
  動作中に `scan` (Wire で 1〜126 を叩く) を送ると `Guru Meditation Error: Core 1 panic'ed (Store access fault)`、`MTVAL 0x0000ffff`、`A2 0x500c4000` (I2C0 のレジスタ)
- 原因: ESP32-P4 では M5Unified が内部 I2C を **I2C1 (G31/G32)**、Port A を **I2C0 (G53/G54)** に割り当てる (`M5Unified.cpp` の `in_port` / `ex_port`)。
  `cfg.external_display_value` の既定は `0xFFFF` で、`M5.begin()` が Unit OLED などを探しに **M5GFX 自前の I2C ドライバで I2C0 を初期化する** (`M5Unified.hpp` の `if (cfg.external_display_value)`)。
  そのあと Arduino の `Wire` (I2C0) を開くと、同じペリフェラルを 2 つのドライバが触る
- **仮説 1 (外れ)**: `cfg.external_display_value = 0;` + `M5.Ex_I2C.release()` にしても症状は同じだった
- クラッシュ番地を `riscv32-esp-elf-addr2line` で戻すと `i2c_ll_read_rxfifo` ← `i2c_isr_receive_handler` (`esp_driver_i2c/i2c_master.c:770`)。
  **Arduino の Wire (i2c_master ドライバ) の ISR が、受信バッファの無いところへ RX FIFO を書き込んで落ちている** = 自分が始めていない転送のデータを受け取っている
- 別の機器 (M5Stack Basic) で踏まなかったのは、Basic は内部 I2C と Port A が同じ G21/G22 で、`in_port == ex_port` になるため (と考えている。未確定)

### 切り分け: M5Unified を外した素の Wire (`m1_i2c_diag/`) — 2026-09-12

- M5Unified も M5GFX も使わず、`Wire.begin(53, 54, 100000)` だけで QR ユニットのレジスタを 1 秒ごとに読む
  (Port A の 5V は IO エキスパンダが前のファームの状態を保持しているので、M5Unified 無しでも給電されている)
- **レジスタ指定の後に STOP を入れない読み方 (`i2c_master_transmit_receive`) でも、入れる読み方 (`i2c_master_transmit` → `i2c_master_receive`) でも全部読めた**:
  `#DIAG probe=0 fw=1:0x03 mode=1:0 ready=1:0 ... ok=29 ng=0`。ファーム版数 `0x03` / トリガモード `0` (AUTO)
- → ESP32-P4 + Arduino Wire + Unit QRCode の組み合わせ自体は正常。~~M5Unified と同居させたときだけ壊れる~~ (**誤り。下の「真因」を参照**)
- ビルドの `DebugLevel=verbose` で `esp32-hal-i2c-ng.c` の転送ログが USB シリアルに出る (`i2cWriteReadNonStop(): i2c_master_transmit_receive: bus=0 ...`)
- 踏んだこと: `serial.ps1` の出力を `Select-Object -First N` で途中で切ると、子プロセスが指定秒数が過ぎるまで COM3 を掴んだまま残り、
  直後の `serial.ps1` が開けない。**出力はファイルに落としてから絞り込む**

### 切り分け 2: M5.begin() の前後 (`m1_i2c_diag2/`) — 2026-09-12

- A: `M5.begin()` の前 / B: 直後 / C: `Wire.end()` → `Wire.begin()` の後 / D: loop で `M5.update()` を回しながら、の 4 段階で読んだ
- **全段階で全部読めた** (`#DIAG ... ok=28 ng=0`)。**M5Unified との同居は犯人ではなかった**

### 真因: M5UnitQRCode 1.0.0 が I2C の速度を `uint8_t` に切り詰めて 160Hz にしている

- `M5UnitQRCodeI2C.h` のメンバが `uint8_t _speed;`。`begin(&Wire, addr, sda, scl, 100000)` は `_speed = speed; _wire->begin(_sda, _scl, _speed);`
  → **`100000` が `160` (Hz) になって `Wire.begin()` に渡る**
- 壊れた `m1_bringup` だけが Wire の初期化をライブラリに任せていた。切り分けの 2 本は自分で `Wire.begin(53, 54, 100000)` を呼んでいた
- 160Hz だと 1 ビット 6ms 超。レジスタ指定 2 バイト + 読み 1 バイトで 170ms を超え、Wire の既定タイムアウト 50ms で打ち切られる
  → 読み取りが毎回 `0xFF`、アドレスだけの probe は通る、打ち切り後に遅れて届いた受信割り込みで `i2c_isr_receive_handler` が落ちる。**症状と全部合う**
- 対処: **ライブラリを呼ぶ前に `Wire.begin(53, 54, 100000)` を自分で呼び、後で `Wire.setClock(100000)`**。本体ファームでは M5UnitQRCode を使わず、
  レジスタ表 (`0x0000` TRIGGER / `0x0010` READY / `0x0020` LENGTH / `0x0030` TRIGGER_MODE / `0x1000` DATA / `0x00FE` FW) を使って自前で読む
  (ライブラリの `readBytes()` は `requestFrom` の失敗も検出しない)
### 実物の QR をかざした結果 (`qrlog`) — 2026-09-12

`tools/test_qr.html` を PC の画面に出して、 QR ユニットにかざした (2 回に分けて計 61 回読取)。

- **読めた**: `1234567` / `7654321` / `AB` / `tw-025` / `ABCDEFGHIJKLMNO` (15) / `ABCDEFGHIJKLMNOP` (16) / `12345678` / `123456` /
  `MM-100/A_1#` / `X` / `A B` / `T,01`。**I2C の失敗は 61 回中 0 回**
- **1 次元バーコード (EAN13 の JAN、Code128) は読めなかった** (PC の画面に表示したもの)。
  **2026-09-13 に実物の商品の JAN もかざしてもらったが読めなかった → 1 次元バーコードは仕様から外す**。
  ユニット側の設定で読めるようになるかは調べていない
- 大文字の `TW-025` (QR) はログに出ていない (かざしていないのか、読めないのかは未確認)
- **末尾に CR/LF は付かない** (hex で確認)
- **READY は 1 と 2 の両方が出る** (M5Stack Basic の別の機器で見た現象と同じ。0 以外なら読み出す作りが要る)
- かざしている間、AUTO スキャンは同じコードを 1 秒に何度も読む → 本体では同じコードを 3 秒読み捨てる (計画どおり)
- タッチ座標は縦 720×1280 の向きのまま取れる (`TOUCH x=555 y=292` など)
- **画面の書き換えが遅いと分かった。** CPU は既に 360MHz (P4 rev<3 の最高)。タッチや読取のたびに全面を塗り直していた → M2 で描画時間を測る

## M2 省電力・描画 (`m2_power/`) — 2026-09-12

### 描画時間 (360MHz)

- 全面を塗り直す (`fillScreen` + 日本語の文字列): **平均 39.3ms** (5 回)
- QR の区画だけ: **平均 3.4ms** / タッチの区画と印だけ: **1.4ms**
- **変わった区画だけ書き直すようにしたら、体感で「タッチの反応はすごくいい」。** M1 の遅さは CPU ではなく全面の書き直しだった
  (M1 の時点で CPU は既に 360MHz で、P4 rev<3 ではこれが最高)

### CPU を 40MHz / 20MHz に落とすと再起動する

- `setCpuFrequencyMhz(40)` / `(20)` は `ok=1` を返し `getCpuFrequencyMhz()` も変わるが、直後に
  `E lcd.dsi: can't fetch data from external memory fast enough, underrun happens` → `rst:0x7 (HP_SYS_HP_WDT_RESET)`
- MIPI-DSI の画面は PSRAM のフレームバッファを流し続けているので、CPU を落とすと供給が間に合わずハードウェアのウォッチドッグで落ちる
- **→ 画面を点けている間 (減光中も) は 360MHz から落とせない。** 計画の「待機・減光・消灯は 40MHz」は取り下げ、
  電力は明るさ・パネルスリープ・QR の間欠・使わない電源の遮断で稼ぐ
- 消灯中に DSI の送出そのものを止めれば落とせる可能性はあるが未検証 (M5GFX の `sleep()` はパネルに SLPIN を送るだけ)

### INA226

- USB 給電だけで `bat_mv=8388 bat_ma=0 vbus_mv=-1 charging=0 level=100`。**電流は 0 のままで、全体の消費は読めない**
  → 省電力の効果は USB 電力チェッカーで測る

### その他

- 大文字の `TW-025` (QR) も読める (M1 で出なかったのはかざしていなかっただけ)
- Arduino のビルド済み sdkconfig はコアダンプをフラッシュに残す設定 (`CONFIG_ESP_COREDUMP_ENABLE_TO_FLASH`)。既定パーティションに `coredump` 領域がある
- タスク WDT 5 秒 / 割り込み WDT 300ms (`CONFIG_ESP_TASK_WDT_TIMEOUT_S` / `CONFIG_ESP_INT_WDT_TIMEOUT_MS`)
- **無線モジュール C6 の電源 (`M5.getIOExpander(1).digitalWrite(0, false)` = 0x44 bit0) と USB-A の 5V (`setExtOutput(false, ext_USB)`) を切っても、
  画面 (全面 37.7ms)・QR の I2C・情報取得はそのまま動いた。** 戻しても問題なし。電流の差は測れていない (USB 電力チェッカー待ち)

## M2 保存・時刻・ライトスリープ (`m2_nvs/`) — 2026-09-12

### NVS パーティション `tooldb` (スケッチ直下の `partitions.csv`)

- **arduino-esp32 3.3.11 はスケッチ直下の `partitions.csv` を使う** (`platform.txt` の `recipe.hooks.prebuild.3.pattern` がビルド先へコピーする)。FQBN の `PartitionScheme` 指定は要らない
- `esp_partition_find_first(DATA, NVS, "tooldb")` → `addr=0xc90000 size=0x100000`。`nvs_flash_init_partition` は `ESP_OK`、**総エントリ 32,256**
- `Preferences.begin(ns, false, "tooldb")` で読み書きできる。**15 文字のキーは書ける / 16 文字は `putString` が 0 を返して書けない**。記号入り (`TW-025/A_1#.x`) も可
- `nvs_entry_find` / `nvs_entry_next` で名前空間ごとに列挙できる (最後は `ESP_ERR_NVS_NOT_FOUND`)
- **32 バイトの blob を 400 件 (記号入り 15 文字のキー) 書いて 452ms、使ったのは 1,208 エントリ (1 件 3 エントリ)**。計画の見積もり (貸出 100×3 + 履歴 100×4 + 開閉ログ 200×3) と合う
- `nvs_flash_deinit_partition` → `nvs_flash_erase_partition` → `nvs_flash_init_partition` で消して開き直せる
- **ソフトの再起動 (`ESP.restart()`) の後も全部残っていた。**
- **USB を 10 秒以上抜いた後も残っていた** (09-12 22:33 JST に抜き差し → 09-13 06:23 JST に確認)。
  `app` の 3 件は値まで一致、`stats used=1208 namespaces=2` も書いた直後と同じ (`loans` の 400 件を含む)
- 抜き差しから 8 時間後に初めて COM3 を開いたとき、**1 回だけ `rst:0x17 (CHIP_USB_UART_RESET)` で再起動した**。
  続けて 2 回開いたときは再起動しなかった。原因は未確認 → 統合ファームで「PC を繋いで最初に開くと再起動するか」を確かめる
  (再起動すると、SD が無いときに RAM だけに持つ無登録の写真が消える)

### RTC

- 何も設定していない RTC は `2048-01-05T09:02:08` (でたらめな値)。`getVoltLow()` は 0 だったので、**電圧低下フラグだけでは「時刻未設定」を判定できない** → 計画どおり「2026 年より前」でも判定するが、2048 年のような未来の値も弾く必要がある
- `M5.Rtc.setDateTime({{2026, 9, 12}, {12, 50, 0}})` → ソフトの再起動を挟んで 10 秒後に `12:50:10`
- **USB の抜き差し (10 秒以上) をまたいで時計は進み続けていた。** 設定値は実際の時刻と無関係に入れたので、PC の UTC との差で比べた:
  - 設定直後 (09-12 22:26 JST): RTC − UTC = −35 分 50〜57 秒 (`12:50:10` を読んだコマンドの終了が UTC 13:26:07)
  - 8 時間後、抜き差しを挟んで (09-13 06:25 JST): −35 分 50 秒 (`20:49:42` を UTC 21:25:31.3〜34.5 に読んだ)
  - ずれは測り方の粗さ (数秒) の範囲に収まる。`volt_low=0` のまま
- 固まっていた本体が抜き差しで戻った = 電源は本当に落ちている (NP-F550 は付いていないとみられる)。
  **バックアップはスーパーキャパだけなので、何分まで抜いていられるかは未確認**

### 手動ライトスリープ

- `M5.Display.setBrightness(0)` + `sleep()` の後、`esp_light_sleep_start()` を 200ms のタイマ復帰で 10 回
- **`#LSLEEP begin` の後、USB シリアルが無音になり、コマンドにも応答しなくなった。** COM3 自体は Windows 上に残る
- **画面を確認: 真っ黒のまま、QR をかざしても画面が変わらない。** USB だけでなく本体ごと止まっている (復帰しない)
- **→ 消灯中の手動ライトスリープは不採用。** 消灯中の省電力はバックライト 0・パネルスリープ・QR の間欠・使わない電源の遮断で稼ぐ。
  (MIPI-DSI の送出が止まったまま戻らない / PSRAM の半スリープ / USB-Serial/JTAG のどれが原因かは切り分けていない。採用しない以上、深追いしない)

- **別の機器 (M5Stack Basic) も同じライブラリを同じ呼び方で使っている。** 古い ESP32 では 160Hz が作れず別の値に丸められていた可能性があり、
  その機器で踏んだ「READY が張り付く」「I2C の失敗を検出できない」とも関係するかもしれない (未確認)

## M2 音・明るさ・電流 / M3 microSD (`m2_bench/`) — 2026-09-13

### 音 (耳で確認)

- 鳴らし方: 操作音 = 2400Hz 70ms / 警告 1 = 2000Hz を 300ms 鳴らして 300ms 休む (断続) / 警告 2 = 2800Hz と 2000Hz を 250ms ずつ交互 (連続)。
  音量は `M5.Speaker.setVolume(百分率 × 255 / 100)`
- **警告 1 と警告 2 ははっきり聞き分けられる**
- **30% の警告でも工具箱の前で気付く** → 警告の音量の下限は 30% のまま
- **100% の警告 2 はうるさすぎる。60 / 70 / 80% を聞き比べて 60% を既定にした** → 警告 1 の既定は 20% 低い 40%
- 操作音 (既定 50%) はそのままでよい
- 起動直後 (まだ鳴らしていない) の IO エキスパンダ 0x43 の出力は `0x74` で、bit1 (アンプ) は 0 だった

### 明るさ (目視)

- 100 → 60 → 30 → 15 → 10 → 5 → 2% を 4 秒ずつ
- **減光の既定 15% で文字は読める / 通常の明るさの下限 10% は妥当 / 通常の既定 60% はちょうどよい** → 既定値と範囲は変えない

### IO エキスパンダ (起動直後、M5Unified の初期化のまま)

- 0x43: `dir=0x73 out=0x74` / 0x44: `dir=0xB1 out=0x89` (0x44 の bit0 = C6 の電源 ON、bit7 = 充電 ON)

### microSD (SPI: CS 42 / SCK 43 / MOSI 44 / MISO 39、20MHz)

- `SPI.begin(43, 39, 44, 42)` → `SD.begin(42, SPI, 20000000)` で開けた (260ms)。SDHC (`cardType=3`)、`cardSize` 30,436MB
- 長いファイル名 `/ToolCheck/photos/20260913-061500-2.jpg` に書いて読み戻し、中身は一致。`exists` / `remove` も正しい
  - 200KB: 書込 156ms / 読み戻し 125ms
  - 2MB: 書込 1,543ms (約 1.3MB/s) / 読み戻し 1,251ms (約 1.6MB/s)
- → 写真 1 枚 (数百 KB) の書込は 1 秒かからない見込み
- 変種 (`pins_arduino.h`) は `BOARD_HAS_SDMMC` スロット 0 だが、SDMMC の電源チャネルが Tab5 で何に当たるか分からないので試していない (SPI で足りる)
- 抜き差しの検出・書込中の電源断・100 枚を超えた削除は未確認

### 電流 (USB 電力チェッカーで読んだ。USB 給電 4.91V、NP-F550 なし、microSD あり)

`seq 30` (1 手順 30 秒、前の手順の状態に 1 つずつ足していく) を流し、読み切れなかった手順を測り直した
(1〜6 = 1 回目、7 = 手順 6 の状態から単独で 60 秒、8〜10 = 2 回目)。

| 手順 | 状態 | 電流 | 前の手順との差 |
|---|---|---|---|
| 1 | 基準: 明るさ 60%・C6 ON・USB-A ON・QR 自動・スピーカー有効 | 0.57A | — |
| 2 | QR を手動 | 0.45A | −0.12A |
| 3 | QR を自動に戻し、C6 を OFF | 0.45A | ±0 (手順 1 との差 −0.12A) |
| 4 | さらに USB-A の 5V を OFF | 0.47A | +0.02A |
| 5 | さらに明るさ 15% | 0.39A | −0.08A |
| 6 | さらに明るさ 0 | 0.31A | −0.08A |
| 7 | さらにパネルスリープ | 0.29A | −0.02A |
| 8 | さらに QR を手動 | 0.26A | −0.03A |
| 9 | さらにスピーカー停止 (アンプ OFF) | 0.25A | −0.01A |
| 10 | 全部戻す | (0.23A) | 3 秒しか保たない手順で、戻る前の値を読んだとみられる。使わない |

- **C6 の電源 OFF で約 0.12A (約 0.6W) 減る** (手順 1 と 3。どちらも QR 自動)。本体ファームで起動時に切る計画どおりでよい
- **USB-A の 5V OFF は差が出ない** (何も挿していない)。切っても害はないので計画どおり切る
- **明るさ 60% → 15% で約 0.08A、15% → 0 でさらに約 0.08A**。パネルスリープの上乗せは約 0.02A
- **QR を手動にしたときの減り方が 2 回で違う** (画面 60% のとき −0.12A、画面を消した後は −0.03A)。
  手順 2 は QR だけを変えたので −0.12A は QR の差と言えるが、手順 8 で小さかった理由は分からない (未確認)
- 一番絞った状態 (手順 9) で **0.25A × 4.91V ≈ 1.2W**。CPU は画面を点けておくために 360MHz 固定

### 問題と切り分け

- **ISP がセンサーのゲインを SCCB で書くのが断続的に失敗する** (`sccb_i2c: ... failed to i2c transmit` → `ISP: failed to set pixel gain`)。
  M5GFX は P4 の I2C を LL (`i2c_ll_*`) で直接叩いており、ESP_Video は IDF の `i2c_master` で同じペリフェラルを使うので、ロックを共有していない。
  **`M5.update()` (タッチの読み取り) を止めると 10 秒で 7 回 → 0 回**。本体ファームではカメラが取り込んでいる間は内部 I2C を使わないようにする必要がある
- **色が紫・青っぽい** (画面でも JPEG でも。目視)。`M5.update()` を止めて SCCB の失敗が 0 になっても変わらなかった
  - **画面と JPEG の経路は正しい**: 赤・緑・青・白の帯も、25 / 50 / 75% の灰色の帯も、画面に直接 (`pushImage(rgb565_t)`) と JPEG の読み戻しの両方で正しく見えた。同じフレームを両方に出しても色味は同じ
  - **ISP の出力そのものが紫**: 取り込み開始直後の 1 枚目は `rgb=112,127,109` (やや緑) だが、2 枚目以降は `rgb=133,80,125`。
    `V4L2_CID_USER_ESP_ISP_WB` を読むと、IPA の AWB が赤 1.88 / 青 1.80 まで上げている
  - AWB を止める `V4L2_CID_AUTO_WHITE_BALANCE` は ISP デバイス (`/dev/video20`) では `errno=3` で通らない。WB のゲインは書けるが (`ret=0`)、IPA がすぐ書き戻す (1.15 → 1.79)
  - ビルド済みライブラリに SC202CS 用の AWB 調整 (`s_ipa_awb_SC202CS_config`) が入っていて、Tab5 のモジュールと合っていないとみられる (未確認)。
    設定を選ぶ `esp_ipa_pipeline_get_config` (`libesp_ipa.a`) は弱シンボルではないので、差し替えるならリンク時の `--wrap` が要る
  - 画面の写し (`createPng`) は `pushImage(rgb565_t)` で描いた中間色を暗く・違う色で返す (パネルの見た目と食い違う)。**色の判断に画面の写しを使わない**
- **回転は PPA (`ppa_do_scale_rotate_mirror`) で 47ms** (ソフトは 830〜880ms。PSRAM を列方向に飛び飛びに読むため遅い)。
  出力バッファはアドレスも大きさも PSRAM のキャッシュ境界 (`esp_cache_get_alignment` = 128) に揃えないと `ESP_ERR_INVALID_ARG`
  (`out.buffer addr or out.buffer_size not aligned to cache line size`)。PPA は反時計回りなので、時計回り 90° は `PPA_SRM_ROTATION_ANGLE_270`
- 1 回目は `live` のプレビューに線が入った。`M5.update()` を止めた 2 回目は出なかった (目視)

### ホワイトバランスの手動設定 (調べた)

- ISP にはゲインを手で書く口がある: `V4L2_CID_USER_ESP_ISP_WB` (`esp_video_isp_wb_t` の `red_gain` / `blue_gain`)、`V4L2_CID_RED_BALANCE` / `V4L2_CID_BLUE_BALANCE` (分母 1000)
- ただし **ISP パイプラインコントローラ (IPA) が有効だと、フレームごとに AWB の結果で書き戻される** (`esp_video/src/esp_video_isp_pipeline.c` の `config_white_balance`)。

- Arduino のビルド済みライブラリは `CONFIG_ESP_VIDEO_ENABLE_ISP_PIPELINE_CONTROLLER=1` で固定。切るにはライブラリを作り直すか ESP-IDF に移るしかなく、切ると自動露出 (AE) も止まる
- AWB の調整 (`esp_ipa` の JSON の `awb`) もビルド時に焼き込まれる。Arduino の `ESP_Video` ラッパーにもホワイトバランスの関数は無い (ゲイン・露出・AE の目標・反転・テストパターンだけ)
- → **Arduino のまま実行時に手動 WB にする方法は無い。色はこのままにする** (2026-09-13)。後で直すなら、写真ごとにソフトで補正するか、ライブラリを作り直す

## M3 の残り: microSD の削除・抜き差し (`m2_bench/`) — 2026-09-13

試験のファイルは専用のフォルダ (`/ToolCheck/prunetest` / `/ToolCheck/stress` / `probe.txt`) にだけ作り、既存の写真には触らない。

### 100 枚を超えた写真の削除 (`sd fill 105 3` → `sd prune`)

- 時刻名の 40KB を 105 件と、名前が一番新しい側に 0 バイトを 3 件作った: 108 件で 6,022ms (1 件あたり約 56ms)
- `sd prune` (0 バイトは消し、名前順で新しい 100 件を残す): 列挙 108 件 708ms / 削除 8 件 67ms / 残り 100 件。
  残った最古は `20260913-060500.jpg` (06:00〜06:04 の 5 件と 0 バイトの 3 件が消えた) で期待どおり
- `openNextFile` の列挙は名前順で返ってきた (`unsorted_pairs=0`)。ただし作った順も名前順なので、FAT が名前順に返すとは言えない。本体でも並べ替えてから選ぶ

### 抜き差しの検出 (`sd watch on` で 1 秒ごとに確認。カードを約 5 秒抜いて挿し直した)

- 挿さっている間: `SD.exists` 1〜3ms / 5 バイト書いて閉じる 11〜15ms
- **抜いた後の最初の確認で `exists=0` (2,163ms)・`write=0` (1,242ms)。抜けている間は 1 回の確認に合計 3 秒以上かかった** (`exists` 1,863ms + `write` 1,242ms)
- `SD.cardType()` は抜けた後の失敗を経て `3` (SDHC) → `4` (`CARD_UNKNOWN`) に変わった。`SD.cardSize()` はマウント時の値 (30,436MB) を返し続けた
- **挿し直すと、`SD.end()` / `SD.begin()` をしなくても次の `exists` (1,988ms) で読めるようになり、書込も通った。** `cardType` も次の確認で `3` に戻った (1 回の観測)
- → 本体への影響: 抜けたかは書込か `exists` の失敗で分かる。**ただし抜けている間は 1 回の確認で数秒止まる。** 計画の「待機中は 5 秒ごとに確認」のままだと、
  SD が抜けている間は 5 秒ごとに 3 秒ずつ画面とタッチが止まる。確認の間隔を空けるか、別タスクで確認する必要がある (M5 で決める)

### 書込中の電源断 (`sd stress` →  USB を抜いて約 10 秒後に挿し直す → `sd mount` → `sd check`)

- 200KB のファイルを 4KB ずつ書き続けた: 1 件 255〜257ms (約 780KB/s)
- 挿し直した後: `sd mount` 294ms で開けた。**`sd check` は 80 件すべて大きさ・中身とも一致** (short 0 / zero 0 / bad_content 0、読み切るのに 10,238ms)。
  書きかけだったはずのファイルは 0 バイトでも残っていなかった (1 回の観測。抜いた瞬間が書込の途中だったかは分からない)
- **挿し直した後に初めて COM3 を開いたとき、`rst:0x17 (CHIP_USB_UART_RESET)` で再起動した** (`#READY` が 2 回出た)。
  M2 で 8 時間抜いた後に見たものと同じで、今回は抜いていたのが約 10 秒。**「電源を入れてから初めて PC から開くと再起動する」可能性が高い** (2 回の観測)。
  現場で保守の PC を繋ぐと、SD が無いときに RAM だけに持つ無登録の写真が消える → 統合ファームで「2 回目以降は再起動しない」も含めて確かめる
- RTC は約 10 秒の抜き差しをまたいでずれなかった (PC の UTC との差は抜く前も後も約 −35 分 50 秒)

### カードが挿さっていないときのマウント (`sd end` → カードを抜く → `sd mount` を 2 回)

- **`SD.begin()` は 2 回とも 921ms かけて失敗した**。マウントしていない状態の `cardType` / `exists` / 書込は 0ms で失敗を返す
- → SD が最初から無い現場で「待機中は 5 秒ごとに確認 (= マウントを試す)」にすると、5 秒ごとに約 1 秒止まる。
  抜けた後の確認 (1 回 3 秒) と合わせて、**SD の確認はメインループで回さない**方向で M5 を設計する
